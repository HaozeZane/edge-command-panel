# Edge Command Agent (Linux)

Outbound WebSocket agent for the Edge Command panel. The agent connects to a
Cloudflare Worker through a hibernating Durable Object, receives shell
commands, executes them locally one at a time, and streams durable, ordered
events back. It never accepts inbound connections and never uses the
Cloudflare management API.

This repository branch (`agent`) contains the Linux agent only. The panel
Worker and web UI live on the
[`web` branch](https://github.com/HaozeZane/edge-command-panel/tree/web).

## Status and scope

- Supported targets: **Linux amd64** and **Linux arm64**. The arm64 binary is
  cross-compiled; no physical arm64 host test is claimed.
- Runtime version for this release line: **0.1.2** (overridable at build time).
- Wire protocol: v1. See [docs/PROTOCOL.md](docs/PROTOCOL.md).
- Real Cloudflare deployment: **UNKNOWN**. No production Worker is verified by
  this branch.
- Durable Object hibernation behavior on the real platform: **UNKNOWN**.
- Cloudflare Free plan account limits and actual usage: **UNKNOWN**.
- Real `systemd` installation on a target machine: **UNKNOWN**. The installer
  is covered by shell-syntax/static checks and a full mocked install run that
  redirects every managed path into `.paseo-scratch` and mocks accounts,
  `systemctl`, `curl`, `install` and `chown`. No live systemd host or real
  account database is exercised by this repository's local verification.

Do not treat these notes as evidence that the panel is running in the cloud.
Local unit tests and cross-compilation only prove the artifacts build and the
Go packages pass their local checks.

## Build

The repository root is the Go module root; build from the checkout root.

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
  -ldflags "-s -w -X main.Version=0.1.2" \
  -o dist/edge-agent-linux-amd64 ./cmd/edge-command-agent

CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath \
  -ldflags "-s -w -X main.Version=0.1.2" \
  -o dist/edge-agent-linux-arm64 ./cmd/edge-command-agent
```

Requires Go 1.22+. The only third-party dependency is
`github.com/gorilla/websocket`.

### Release build

`scripts/build-release.sh` builds both architectures and the release
attachments:

```sh
scripts/build-release.sh                 # version 0.1.2
scripts/build-release.sh agent-v0.1.2    # normalized to 0.1.2
RELEASE_OUTPUT_DIR=/tmp/ecp-release scripts/build-release.sh 0.1.2
```

The default output directory is `.release/agent-v<version>`. Set `GO` to use a
specific Go executable. The script produces exactly these attachments:

| File | Description |
| --- | --- |
| `edge-agent-linux-amd64` | Linux amd64 binary |
| `edge-agent-linux-arm64` | Linux arm64 binary |
| `install.sh` | Installer served by the panel |
| `SHA256SUMS` | SHA-256 of the three files above |

A local `*.receipt.txt` next to the output directory records the build version,
Go version, UTC build time, and the source Git commit when `HEAD` exists. The
receipt is not a release attachment, and a repository with no commit yet is
supported. The script does not call `gh`, Wrangler, or GitHub Actions.

## Install

The panel serves `install.sh` at `/agent/install.sh` (direct mode) or
`/enroll/install.sh` (enrollment mode). Run it as root with the `ECP_*`
variables exported by the one-line command generated by the panel:

Copy the current install command from the panel, or download its
self-contained installer and run `sudo bash install.sh` (root can use
`bash install.sh`). The generated command handles sudo and keeps credentials
out of sudo's command arguments.

The script:

- downloads the `amd64`/`arm64` binary from
  `$ECP_URL/agent/download/$arch` or `$ECP_URL/enroll/download/$arch`
  using headers read from a 0600 temporary file (never argv),
- rejects non-200 responses and files that do not run as an agent binary,
- selects the service account from the invoking account (see below), without
  creating a dedicated `edge-command` user or group,
- validates the target home and every managed path before changing the host,
- takes root-controlled update/execution locks, stops an idle compatible
  service, and confirms systemd reports `inactive`/`failed`
  (a stop error, an unreachable manager or an unknown state aborts) before
  replacing the binary, configuration or state ownership,
- creates `/etc/edge-command-agent/config.json` (0600, owned by the service
  account) and `/var/lib/edge-command-agent` (0700),
- installs a hardened systemd unit
  (`Restart=always`, `KillMode=control-group`, `NoNewPrivileges=yes`,
  `ProtectSystem=strict`, `PrivateTmp=yes`,
  `ReadWritePaths=/var/lib/edge-command-agent`),
- enables and starts the service, and exits non-zero unless it is active.

Use `--no-start` to install and validate without enabling/starting. On an
upgrade, `--no-start` still stops a running service and leaves it stopped.

### Service account

The agent runs as the account that installed it:

- **Plain root install:** the target is `root`.
- **Install through `sudo`:** the target is `SUDO_USER`, but only when both
  `SUDO_USER` and `SUDO_UID` are present and agree with the NSS account
  database (`getent passwd`, `getent group`, `id -u` and `id -g`). The primary
  GID and home directory are taken from NSS; inherited `HOME` and `SUDO_GID`
  are not trusted.
- Missing, incomplete or contradictory sudo metadata is rejected before any
  host change. So is a target home that is relative, contains control
  characters or `..` components, is missing, or is a symlink.

The systemd unit uses the target user/group, sets `WorkingDirectory` and
`HOME` to the NSS home directory (`WorkingDirectory=~` selects the
service account home; `HOME` is escaped as a systemd environment assignment), and lets systemd
apply that account's supplementary groups from NSS. When the target account is
already in use, the installer does not delete it; a legacy `edge-command`
account from an older install is left untouched.

Running the agent as the same UID as the installer is **not** the same as
giving the service a full interactive login shell. The service still runs
under `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes`, and a
single writable `ReadWritePaths` state directory; it has no TTY and no login
session. Conversely, a root install means commands execute with UID 0, so
those systemd restrictions limit but do not make root harmless. Prefer
installing through a non-root sudo account unless root execution is required.

### Upgrade behavior

The installer refuses a running legacy service that does not use the new
execution lock. For the first migration from v0.1.1 or older, confirm all
commands have completed, then run:

```sh
sudo systemctl stop edge-command-agent.service
# Run the latest install command copied from the panel next.
```

After migration, manual reinstalls and automatic updates acquire the same
execution lock before stopping the service. A running command makes them
postpone or refuse the operation. Commands submitted during the short update
window are recorded as failed with reason `updating`; they are not retried
or executed later automatically. Already completed command IDs keep their
existing duplicate suppression behavior.

The fixed config/state paths, installation key, and journal are preserved by
automatic updates. Enrollment reinstalls reuse a valid local config; direct
reinstalls explicitly replace it with the selected machine's credentials.
`--no-start` also stops an existing update timer and leaves the agent stopped.

### Automatic stable updates (v0.1.2+)

New installs enable `edge-command-agent-update.timer`. The first check is
5–10 minutes after activation; subsequent checks are approximately every
hour plus 0–5 minutes of random delay. Checks go directly to public GitHub;
there is no extra Worker/DO polling or GitHub token on the machine.

The fixed official repository is `HaozeZane/edge-command-panel`. The updater
examines at most three pages of 100 releases, ignores drafts, prereleases and
non-Agent releases, and chooses the highest strictly numeric
`agent-vMAJOR.MINOR.PATCH` above the installed version. It never downgrades.
It verifies `SHA256SUMS`, the binary SHA-256, ELF architecture, and reported
version before taking the execution lock. Downloads require HTTPS and exact
GitHub release host allowlisting. It never downloads or executes `install.sh`.
This trusts GitHub HTTPS and the repository's publishing authority; the hash
is an integrity check, not an independent publisher signature.

The Agent keeps its original account, home, config, journal and all existing
systemd restrictions. A separate root-owned bootstrap at
`/usr/local/lib/edge-command-agent/bootstrap` manages only the fixed Agent
binary and service. It does not read panel credentials or Agent-provided
update URLs/paths. The root transaction directory is
`/var/lib/edge-command-agent-update` (0700); the root-owned execution lock is
`/var/lib/edge-command-agent-lock/execution.lock` (0644). Install paths and
ancestors must be root-owned and not writable by another account. The Agent
receives no sudo grant. The bootstrap itself is refreshed by reinstalling;
normal automatic updates replace only the main binary.

A verified candidate is cached when a command is busy. The exclusive lock
covers service stop, atomic binary replacement, READY notification, and
30 seconds of stable process health. Readiness does not require the panel or
network to be available. A failed start or health check restores the old
binary and restarts it; the last known good binary is retained. A durable
transaction, root-owned pending fence, and boot recovery unit handle an updater
killed during the switch. The fence keeps new commands blocked even after a
killed updater releases its kernel locks. Recovery also respects running commands. The updater does not start
an intentionally stopped Agent except to recover an interrupted transaction.

Failures back off for 1, 2, 4, 8, 16, then at most 24 hours. GitHub rate-limit
reset/Retry-After can extend this; anonymous limits are shared by machines
behind the same public IP. Failed version/digest pairs are quarantined for
24 hours. A rollback failure blocks further updates and retains its
transaction for operator repair, rather than continually restarting services.

```sh
systemctl status edge-command-agent-update.timer
sudo journalctl -u edge-command-agent-update.service -n 100 --no-pager
sudo journalctl -u edge-command-agent-recover.service -n 100 --no-pager
# Disable automatic checks (boot transaction recovery remains available):
sudo systemctl disable --now edge-command-agent-update.timer
```

If recovery is blocked, stop the timer and inspect the journal and the
root-only `transaction.json` before changing files. Keep that evidence and
`old-binary`. With the Agent stopped, an administrator can verify and restore
the saved known-good binary, archive the updater state, and reinstall. Do not
delete `/var/lib/edge-command-agent` or re-enroll to repair an update: those
contain the machine identity and command history.

## Credentials and enrollment modes

The agent never receives Cloudflare management credentials. Access Service
Tokens are only sent as `CF-Access-Client-Id` / `CF-Access-Client-Secret`
headers.

- **Direct mode (one credential set per machine):** the panel issues an agent
  Service Token bound to that machine's agent identity. Set `ECP_AGENT_ID`,
  `ECP_CLIENT_ID`, and `ECP_CLIENT_SECRET`.
- **Enrollment mode (batch registration credential):** the batch
  registration Service Token authenticates `/enroll/*` and may be reused
  across multiple machines during a short enrollment window. It is a shared,
  time-boxed batch credential, not a per-machine credential. Distribute it
  only through a trusted channel, keep the window short, and rotate or revoke
  it after the batch. Each machine still
  generates its own installation identity and receives its own agent
  credentials and Agent ID.

In both modes `install.sh` derives the mode from `ECP_AGENT_ID` unless
`ECP_MODE` is set explicitly. Keep `ECP_CLIENT_SECRET` out of shell history,
`argv`, and logs.

## Configuration

`-config` defaults to `/etc/edge-command-agent/config.json`.

```json
{
  "url": "wss://panel.example.com/agent/ws",
  "agentId": "…",
  "clientId": "…",
  "clientSecret": "…",
  "stateDir": "/var/lib/edge-command-agent"
}
```

`https://` is converted to `wss://`. Plaintext `ws://`/`http://` is accepted
only for loopback development hosts; production must use WSS. The config file
must be mode 0600. The secret is never logged and never accepted on argv.

Commands run as `/bin/sh -c <command>` in the service account home (the
systemd `WorkingDirectory` is the target home), with stdin connected to
`/dev/null`, one run at a time, in a dedicated process group. The agent does
not sandbox or privilege-separate individual commands; they run under the
same UID/GID and supplementary groups as the service. The systemd hardening
described above still applies to every command.

## Enrollment

Enrollment registers this machine once and writes the final 0600 config. A
valid existing config is reused without contacting the panel and without
consuming enrollment quota. Only a genuinely absent config starts
registration. An existing config that is corrupt, has unsafe permissions or
is not a regular file is a hard error: it is not overwritten and no
challenge/register request is made. A dangling symlink at the config path is
also rejected. `configure` keeps its explicit-overwrite behavior for direct
mode.

```sh
ECP_URL=https://panel.example.com ECP_CLIENT_ID=… ECP_CLIENT_SECRET=… \
  edge-command-agent enroll -config /etc/edge-command-agent/config.json \
  -state-dir /var/lib/edge-command-agent
```

The installation identity (`installationId` UUID + ed25519 keypair) is stored
in `<stateDir>/installation.json` (0600) and is reused across retries and
re-registrations. Enrollment signs:

```
ECP-ENROLL-V1
<challenge>
<installationId>
<hostname>
<publicKey base64 raw 32 bytes>
```

## CLI

```
edge-command-agent [-config path]          # run (default)
edge-command-agent run [-config path] [-execution-lock path]
edge-command-agent enroll [-config path] [-state-dir path]
edge-command-agent configure [-config path] [-state-dir path]
edge-command-agent version
# Fixed-purpose root service operations (normally managed by systemd):
/usr/local/lib/edge-command-agent/bootstrap bootstrap update
/usr/local/lib/edge-command-agent/bootstrap bootstrap recover
```

`configure` builds a direct-mode config from the environment
(`ECP_URL`, `ECP_AGENT_ID`, `ECP_CLIENT_ID`, `ECP_CLIENT_SECRET`,
optionally `ECP_STATE_DIR`). `ECP_URL` is the panel base URL; direct mode
derives the full `/agent/ws` endpoint (an already-full `/agent/ws` URL is not
duplicated).

## Durability and protocol

- Wire protocol is JSON v1, frames capped at 64 KiB.
- Accepted is fsynced to the journal **before** spawn. Every event is
  persisted (fsync) before it is sent. ACKs are persisted before advancing the
  replay watermark.
- Replay always resumes at `ackSeq+1`; a duplicate `execute` never spawns and
  replays the journal (rewinding if the server had acknowledged everything).
- The journal lives at `<stateDir>/runs/<runId>.jsonl`, is capped at 256 MiB,
  and keeps terminal run IDs for 30 days for duplicate suppression.
- A restart marks any non-terminal run `finished/interrupted`; it never
  resumes execution.
- Output is capped at 1 MiB per run (stdout+stderr), coalesced at 16 KiB or
  2 seconds, and keeps draining/discards beyond the cap while reporting
  `outputTruncated`.
- Timeouts send SIGTERM to the process group, wait 5 seconds, then SIGKILL,
  including descendants after the main shell exits.
- Control PING every 30 seconds, reconnect after 90 seconds without PONG,
  exponential backoff 1–60 seconds with jitter.
- `probe` is answered immediately and is not blocked by a running command.
- One state directory is protected by an exclusive `flock`; a second process
  exits instead of running commands.

## Tests

```sh
go test ./... -race
go vet ./...
gofmt -l cmd internal
sh -n install.sh
bash -n install.sh
```

The suite covers exit codes, stdout/stderr, burst output, 1 MiB truncation,
timeout/descendant cleanup, duplicate suppression, restart interruption,
disconnect while a command keeps running with ACK-loss replay, probes,
CF-Access headers, secret redaction, enrollment signatures/retries/reuse,
refusal to overwrite corrupt or unsafe configs, invalid configs and plaintext
URL rejection, journal limits, disk/lock failures, and install-script
syntax/security guards. The installer is additionally executed end-to-end
against a copy whose fixed paths are redirected into `.paseo-scratch`, with
mocked `id`/`getent`/`systemctl`/`curl`/`install`/`chown`: root and sudo
identity selection, unit escaping, unchanged sandbox directives,
stop-before-migration ordering, `--no-start`, metadata/download/stop failures,
symlink rejection, and preservation of config, installation identity and
journal.


Automatic-update verification covers actual subprocess flock contention,
killing updater subprocesses at durable stages, boot/runtime recovery,
wrong hashes/architectures/versions, unsafe redirects, rate limits, cached
busy candidates, post-rename failure rollback, and readiness without network.
The four generated units are additionally checked with `systemd-analyze
verify`. These checks do not constitute a live systemd-host update test; that
remains UNKNOWN, and arm64 is cross-compiled only.
